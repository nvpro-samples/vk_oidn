# Validation and performance

This document records how vk_oidn was validated and measured, with all the numbers obtained
during its development, so the results can be reproduced and regressions detected. How the
library works is described in [architecture.md](architecture.md).

## Test environment

| Item               | Value                                                              |
|--------------------|--------------------------------------------------------------------|
| GPU                | NVIDIA RTX PRO 4500 Blackwell (Vulkan 1.4.351, driver 617.42)      |
| Second GPU         | AMD Radeon integrated graphics (RDNA2, driver 26.8.1), used only for portability checks |
| OS / compiler      | Windows 11, MSVC 19.44 (Visual Studio 2022), Release builds        |
| Vulkan SDK         | 1.4.363.0 (validation layer, glslang 16.6.0)                       |
| Slang              | 2026.17 (from the Vulkan SDK)                                      |
| OIDN reference     | official Open Image Denoise 2.5.1 Windows binaries (CPU and CUDA devices) |

## Test images

The images are synthetic, generated by [`tests/scripts/gen_images.py`](../tests/scripts/gen_images.py):
a lit checkerboard with a sphere and a bright spot, rendered with Monte Carlo-like noise (average
of 4 exponentially distributed samples per pixel with rare fireflies), plus noise-free albedo and
normal images. Three sizes were used: 333x197 (odd size, exercises partial tiles and borders),
1920x1080 and 3840x2160.

```
python tests/scripts/gen_images.py images/odd 333 197
python tests/scripts/gen_images.py images/hd 1920 1080
python tests/scripts/gen_images.py images/4k 3840 2160
```

## Accuracy metric

The same metric as OIDN's `oidnDenoise -r`: for every channel value, the relative error is
`|expect - actual| / (|expect| + |actual| + 0.01)`. A test passes if the average relative error
(`avgerror`) is at most 0.003 (0.05 for normal filtering) and there is no outlier (a value with an
absolute error above 0.02 *and* a relative error above 0.05).

The reference is always the output of the OIDN 2.5.1 **CPU** device for the same configuration.
On top of the metric, outputs that should be identical were compared **bit for bit** (e.g.
vk_oidn with buffers and with storage image views).

### Issues found and fixed during validation

| Issue | Symptom | Cause | Fix |
|-------|---------|-------|-----|
| Output biased on AMD | avgerror ~0.004 instead of ~0.0003, image 1% darker | the driver rounds FP32 → FP16 conversions toward zero by default | request round-to-nearest-even and FP16 denormal preservation (SPIR-V float controls) in all kernels |
| FP16 images wrong on AMD | avgerror 0.08 with half input images | 16-bit loads from addresses that are not 4-byte aligned (6-byte RGB pixels) returned wrong data | load FP16 pixels with aligned 32-bit loads |
| FP16 storage image output | avgerror 0.00037 instead of 0.00034 | the rounding of the storage image format conversion is implementation-defined | round to FP16 in the shader when the output view format is FP16 |
| Crash on lavapipe (Mesa 25.2) | segmentation fault with a fixed input scale or LDR input | without autoexposure the scale pointer is 0, and the driver performs the load inside the untaken uniform branch | the kernels load the scale from an always valid address, then select it (bit-identical outputs) |

The KHR cooperative matrix path also produced wrong results on the AMD integrated GPU
(RDNA2, no matrix hardware); cooperative matrices are therefore enabled by default only on NVIDIA
GPUs, and other GPUs use the fallback kernel, which passes all tests on the AMD GPU.

## Performance

The reference numbers are the [GPU time](#gpu-time-main-metric) and
[per-image latency](#per-image-latency-secondary-metric) tables below, measured on 2026-10-19 with
the protocol described here. Everything needed to reproduce them (programs, scripts, raw logs) is in
[`docs/benchmarks`](benchmarks). The sections after them (per-layer times, optimization history,
experiments) are development measurements: mostly single runs, comparable within a section but not
with the reference tables.

### What is compared

| Column | Program | Kernels | Host runtime |
|--------|---------|---------|--------------|
| **OIDN 2.5.1 CUDA** | official Open Image Denoise 2.5.1 Windows binaries, CUDA device (its CUDA library contains native code for Blackwell, `sm_120`) | OIDN's CUDA kernels | OIDN |
| **vk_oidn** | vk_oidn 0.2.0 (commit `26555d7`) | vk_oidn's Slang kernels | vk_oidn: everything recorded in the application's command buffer |

The comparison is between two implementations of the same OIDN neural network, with the same
weights: OIDN's CUDA kernels and vk_oidn's Vulkan kernels. It is not a comparison between CUDA and
Vulkan as programming interfaces.

**Workload**, identical for both: RT filter, `hdr + albedo + normal` model, HDR input, FP32 RGB
images in device memory; 1280x720, 1920x1080 and 3840x2160; high and fast quality. 3840x2160 is
processed in 2 tiles by both (OIDN: tile size 2016x2160, 2x1 tiles; vk_oidn: 2 tiles). The inputs
are random, with the distributions of OIDN's `oidnBenchmark` (color in [0, 100], albedo in [0, 1],
normal in [-1, 1]); the time does not depend on the pixel values (vk_oidn, 1920x1080 high, two
different input sets alternated 3 times: 5.576-5.589 ms and 5.589-5.597 ms).

**Machine**: NVIDIA RTX PRO 4500 Blackwell, driver 617.42 (default settings, clocks not locked),
AMD Ryzen 9 7950X, Windows 11 (build 26200). vk_oidn built with MSVC 19.44, Slang 2026.17, Vulkan
SDK 1.4.363.0; `oidn_gpu_bench` built with MSVC 19.51 against the official 2.5.1 SDK and CUDA
12.8 (for the CUDA events only: the denoising runs in the official OIDN CUDA library).

### Metrics

**GPU time (main metric)**: the time per image when denoising runs back to back, as in a rendering
pipeline. Each implementation denoises a warm-up batch of 50 images, then a timed batch of 50
images without waiting between them, and synchronizes once at the end; the time of the timed batch
is divided by 50.

- OIDN 2.5.1 CUDA: [`oidn_gpu_bench`](benchmarks/oidn_gpu_bench.cpp), built against the official
  2.5.1 SDK and run with its DLLs. It creates the buffers in device memory (`OIDN_STORAGE_DEVICE`,
  like `oidnBenchmark`), calls `oidnExecuteFilterAsync` 50 times, then `oidnSyncDevice`, and
  measures the host time from the first call to the end of the synchronization, and the GPU time
  between CUDA events recorded on the device's stream before and after the batch.
- vk_oidn: `vk_oidn_denoise_test -n 50` records 50 `cmdDenoise` calls in one command buffer,
  submits it and waits; it measures the host time from the submission to the end of the wait, and
  Vulkan timestamps written before and after the 50 denoisings.

The tables use the host-measured batch time, the same clock for both; it agrees with the GPU timers
(CUDA events and Vulkan timestamps) within 0.011 ms in every run. OIDN's host code needs 1.1-3.5 ms
per image to enqueue the work at 720p and 1080p and 16.5-24.5 ms at 4K, always less than the GPU
time, so the OIDN batches are bound by the GPU (vk_oidn's batch is a single command buffer).

**Per-image latency (secondary metric)**: the metric of OIDN's `oidnBenchmark`: for each image,
execute and wait for the result; two warm-up runs, then as many runs as fit in 0.5 s (at least
3). OIDN 2.5.1 CUDA is measured with the official `oidnBenchmark`; vk_oidn with
`vk_oidn_denoise_test --bench`, which records the command buffer, submits it and waits for each
image, with the same warm-up and run count rules. This metric adds the host-side work and the
synchronization of every image.

**Repetitions**: every configuration (implementation x 3 resolutions x 2 qualities) was run 5
times, interleaved: round 1 runs all configurations, then round 2, and so on. Each run started
after the GPU utilization had been below 5% for 10 s. The tables give the **median of the 5 runs**
with the minimum and maximum in brackets; ratios are ratios of the medians. The GPU clocks were not
locked: in one round, all implementations were about 8% slower (visible in the maximum values), and
absolute times vary by a few percent between sessions; since the rounds are interleaved, this
affects both columns alike, and the ratios are stable (see the per-round ratios below). The rounds
also ran two internal development builds, which are not part of the published results; their
entries are removed from the published logs.

### Experiment: `VK_NV_cooperative_matrix2`

NVIDIA's cooperative matrix 2 extension (all features supported on this GPU: workgroup-scope
matrices up to 1024 per dimension with M32/N16/K16 granularity for 128 invocations, tensor
addressing, block loads) was tried with a different kernel design
(`shaders/experimental/conv_cm2.comp`, enabled with `VK_OIDN_CM2=1`): one workgroup-scope
accumulator per BM pixels of a row and all output channels, A matrices loaded directly from the
input rows with clamped tensor addressing (which implements the zero padding), no explicit shared
memory. It is used for the layers without pooling/upsampling.

| BM (pixels) | BK (channels) | Total time | dec_conv2b | dec_conv1b |
|-------------|---------------|------------|------------|------------|
| KHR kernel  | –             | **7.11 ms** | 0.509 ms  | 0.943 ms   |
| 32          | 32            | 9.07 ms    | 0.607 ms   | 1.762 ms   |
| 64          | 32            | 9.43 ms    | 0.515 ms   | 1.518 ms   |
| 32          | 64            | 8.95 ms    | 0.633 ms   | 1.670 ms   |
| 64          | 64            | 9.49 ms    | 0.589 ms   | 1.515 ms   |
| 128         | 32            | 10.38 ms   | 1.541 ms   | 1.468 ms   |
| 256         | 32            | 15.02 ms   | 1.549 ms   | 3.248 ms   |

The output is correct (avgerror 0.000340), but this design is 25-30% slower than the tuned
`VK_KHR_cooperative_matrix` kernel, so it is not used by default. Likely reasons: the 3 horizontal
taps reload overlapping input data instead of reusing it, and many small workgroup-scope
multiply-adds each go through the driver's internal staging. Possible improvements: load the 3
taps as one wider K (overlapping rows, with explicit handling of the image borders), larger K per
multiply-add, or using cooperative matrix 2 only for the matrix multiplications while keeping
the explicit shared memory tiling. Note that Slang's tensor addressing currently requires
descriptor-bound buffers, which is why this kernel is written in GLSL.

### Sub-pixel decomposition of the upsampling layers

The four decoder layers `dec_conv*a` convolve a 2x nearest-upsampled tensor (concatenated with a
skip connection). A 3x3 convolution of an upsampled tensor is exactly four 2x2 convolutions of the
low-resolution tensor, one per output phase (row parity, column parity), with combined weights
(along each axis: phase 0 uses offsets {-1, 0} with weights {w0, w1 + w2}, phase 1 offsets
{0, +1} with {w0 + w1, w2}). This removes 56% of the multiply-adds of the upsampled source, which
is most of the work of these layers (e.g. 64 of the 80 input channels of `dec_conv1a`).

In the kernel (`convCoopMatUp`), each 16-pixel matrix fragment holds output pixels of a single
phase (every other pixel of a row), so all its rows use the same combined weights; the
low-resolution source is read from a half-resolution shared memory tile, and the skip connection
with stride-2 rows from the full-resolution tile.

The first version gave each subgroup the 4 phases of 2 rows. It was **slower** (7.79 ms vs
7.31 ms): each weight tile was used by a single fragment, so the kernel became bound by the weight
loads (the original kernel reuses each weight tile for 4 fragments). Giving each subgroup one
phase (4 rows of the same parity) restores the reuse and gives the speedup above: 1.20-1.40x on
the upsampling layers, about 8% overall (1080p high: 7.29 → 6.72 ms, fast: 3.96 → 3.65 ms;
4K high: 30.22 → 27.83 ms, fast: 16.03 → 14.63 ms).

### Weights staged in shared memory

At 89 TFLOPS on average, the kernels used about 45% of the FP16 tensor core peak (next section),
so they were limited by data movement. To find which data, two diagnostic builds of the main
convolution kernel (wrong results, timing only) loaded the input fragments (from shared memory)
or the weight fragments (cooperative matrix loads from global memory) once per chunk instead of
once per tap. 1920x1088, high quality, all layers with 32x8 tiles and 2 output blocks per
workgroup, best of 3 runs:

| Layer | Normal | Input loads once per chunk | **Weight loads once per chunk** |
|-------|--------|----------------------------|---------------------------------|
| enc_conv1  | 0.448 ms | 0.426 ms | **0.292 ms** |
| dec_conv3b | 0.293 ms | 0.284 ms | **0.142 ms** |
| dec_conv2b | 0.514 ms | 0.499 ms | **0.318 ms** |
| dec_conv1b | 0.949 ms | 0.919 ms | **0.623 ms** |
| total      | 6.447 ms | 6.322 ms | **5.312 ms** |

The input loads from shared memory cost little; the weight loads were the main cost. Each of the
4 subgroups of a workgroup loaded the same weight fragments from global memory, just before using
them. Three ways to reduce this were tried:

| Change | 1080p high (balanced) | Result |
|--------|------------------------|--------|
| 4 output blocks per workgroup (`nf4`, 16 multiply-adds per 8 fragment loads instead of 8 per 6) | 7.69 ms (6.82 ms) vs 6.68 ms (6.07 ms) | slower: the weight loads grow with the output blocks, more registers, wasted work for layers with 2 or 6 blocks |
| Weight fragments of the next tap loaded in registers during the current tap (hide the latency) | 6.73 ms (5.88 ms) vs 6.35 ms (5.78 ms) | slower: the cost is the number of loads, not their latency, and more registers |
| **Weights of the chunk staged in shared memory**, loaded once per workgroup with coalesced `uint4` loads | **4.97 ms (4.85 ms)** vs 6.37 ms (5.78 ms) | **1.28x (1.19x)** |

With the weights in shared memory, a chunk needs 9 taps x 2 output blocks x 512 bytes = 9 KB for
the main kernel, and up to 16 KB for the sub-pixel kernel (4 phases x 4 taps). Next to the
double-buffered input tiles (32.6 KB), they only fit single-buffered in the 48 KB available to a
Vulkan workgroup (`maxComputeSharedMemorySize`), so each chunk has two barriers: before
overwriting the weights and before using the new ones. The main kernel pads the weight rows
(48-byte stride, 41.8 KB in total, slightly faster than without padding); the sub-pixel kernel
cannot (49,024 bytes). The 48-pixel-wide tiles no longer fit, but the 32-pixel tiles with staged
weights are faster on every layer, and 2 output blocks per workgroup are now faster even for the
small low-resolution layers (1 block only when the number of blocks is odd).

Per-layer times, 1920x1088, high quality (best of 3 runs):

| Layer | Before | Staged weights | Layer | Before | Staged weights |
|-------|--------|----------------|-------|--------|----------------|
| input      | 0.161 ms | 0.160 ms | dec_conv4a | 0.140 ms | 0.114 ms |
| enc_conv0  | 0.261 ms | 0.252 ms | dec_conv4b | 0.130 ms | 0.071 ms |
| enc_conv1  | 0.445 ms | 0.324 ms | dec_conv3a | 0.372 ms | 0.231 ms |
| enc_conv2  | 0.205 ms | 0.158 ms | dec_conv3b | 0.287 ms | 0.165 ms |
| enc_conv3  | 0.101 ms | 0.058 ms | dec_conv2a | 0.670 ms | 0.528 ms |
| enc_conv4  | 0.059 ms | 0.041 ms | dec_conv2b | 0.506 ms | 0.392 ms |
| enc_conv5a | 0.043 ms | 0.017 ms | dec_conv1a | 1.625 ms | 1.351 ms |
| enc_conv5b | 0.051 ms | 0.020 ms | dec_conv1b | 0.936 ms | 0.748 ms |
| output     | 0.071 ms | 0.070 ms | dec_conv0  | 0.296 ms | 0.259 ms |
|            |          |          | **total**  | **6.373 ms** | **4.965 ms** |

The summation order is unchanged, so the outputs are bit-identical to the previous kernels in all
qualities, and all validation configurations pass with no validation layer errors.

**Larger K chunks** (32 input channels per chunk, half the barriers) were not tried: they double
the shared memory of the input tiles and weights, which is already at the 48 KB limit. They would
need smaller tiles, which reduce the reuse of the staged weights.

Tools for these experiments: `VK_OIDN_CONV_VARIANT=mx2_nf1` forces the number of output blocks per
workgroup, and `VK_OIDN_KERNEL_DIR=<dir>` loads `<dir>/<kernel>.spv` instead of the embedded kernel
(to compare kernel versions with the same library build).

### Tensor core peak, and an experiment with cooperative vectors (`VK_NV_cooperative_vector`)

How far are the kernels from the hardware limit, and could cooperative vectors, the newer
SPIR-V matrix-vector instructions for neural shading, be faster? The micro-benchmarks in
[`tests/microbench`](../tests/microbench) measure this on the RTX PRO 4500 Blackwell
(driver 617.42, Vulkan SDK 1.4.363).

**Tensor core peak** (`VK_KHR_cooperative_matrix`, register-only multiply-add chains, best of 1 to
8 independent chains per subgroup):

| Inputs → accumulator | Peak |
|----------------------|------|
| FP16 → FP16          | 203 TFLOPS |
| FP16 → FP32          | 200 TFLOPS |
| FP8 (E4M3) → FP16    | 399 TFLOPS |
| FP8 (E4M3) → FP32    | 394 TFLOPS |
| INT8 → INT32         | 454 TOPS |

The high quality network does 565 GFLOP per 1920x1088 frame (with padded channels), so 6.36 ms is
an average of 89 TFLOPS: **about 45% of the FP16 peak** (the largest layer reaches 98 TFLOPS,
49%). The kernels are limited by data movement (loading the activation tiles and weight fragments
of each multiply-add from shared and global memory), not by the tensor core math. Staging the
weights in shared memory (next section) raised the average to about 113 TFLOPS (56%). Register use
matters too: in the peak test, 6 or 8 independent FP16 chains per subgroup reach only about
100 TFLOPS (fewer resident warps).

**Cooperative vectors** (FP16, matrices converted to the inferencing-optimal layout with
`vkCmdConvertCooperativeVectorMatrixNV`). The driver reports up to 1024 components, with FP16, INT8
and FP8 matrices. Slang supports them (`CoopVec`, `coopVecMatMulAdd` with pointers), so writing
SPIR-V by hand is not needed; the benchmark kernels use GLSL (`GL_NV_cooperative_vector`).

| Test | Time | Throughput |
|------|------|------------|
| Matrix-vector chain 32x32 / 64x64 / 128x128 (input in registers) | - | 135 / 86 / 82 TFLOPS |
| 3x3 convolution 64 → 64 channels, 1920x1088 (154 GFLOP), 9 products of 64x64 per pixel | 38.5 ms | 4.0 TFLOPS |
| same, 3 products of 64x192 per pixel (3 adjacent input pixels are contiguous) | 42.8 ms | 3.6 TFLOPS |
| same, input vectors computed instead of loaded (products only), 9 / 3 products | 1.18 / 0.94 ms | 131 / 165 TFLOPS |
| same, products replaced by the loaded vectors (memory traffic only) | 1.71 ms | - |
| vk_oidn FP16 kernel on comparable 64-channel layers (`dec_conv2b`, `dec_conv1b`) | ≈2.0 ms | 76-77 TFLOPS |

The products alone and the memory traffic alone are both fast, but together the convolution is
about 20 times slower than vk_oidn's kernel. Changing the workgroup shape, using a single matrix,
removing the bias, not unrolling the taps, or adding arithmetic between the load and the product
does not change it. The fast path of cooperative vectors seems to need inputs computed in
registers, as in per-pixel MLPs (neural materials, texture decompression); a convolution, whose
inputs are neighboring pixels in memory, does not fit it with this driver. Even in the
products-only case, the throughput (131-165 TFLOPS) would leave little room over a better
cooperative matrix kernel.

**Conclusion:** cooperative vectors are not a way to speed up vk_oidn. The headroom is in data
movement (up to about 2x to the FP16 peak) and in FP8 (2x the math peak and half the bytes moved).

## Ideas for further speedups

- Less data movement per multiply-add in the FP16 kernels (the measured peak is still about 1.8x
  the average after staging the weights): double-buffered weights to remove the second barrier
  per chunk, or larger K chunks, which need more than the 48 KB of shared memory available to a
  Vulkan workgroup (smaller tiles or a different input layout).
- FP8 (E4M3) cooperative matrices: 2x the FP16 peak and half the bytes for weights and activations.
  The FP16-trained weights would need a quantization accuracy analysis (per-channel scales), and
  probably quantization-aware fine-tuning with the Open Image Denoise training scripts.
- Smaller networks: for real-time use, a network designed for the budget (as DLSS is) does much
  less work per pixel than the Open Image Denoise U-Net, which targets offline quality.
